# Redo a cross-task subtask move

Redo is a new guarded transfer after a confirmed Undo. Both current tasks, their generations/projects, both structure revisions, the destination parent incarnation/slot and every moved node version must still match the original move/Undo chain. It never resends the old forward request and never copies historical task content into either root.

The private journal keeps its existing wire/file format. Under its account/process lock, Redo requires the exact original and Undo proofs still on disk. Two windows recover one already saved Redo identity rather than queueing duplicate actions. Unknown replies keep the encrypted original request for status/retry. Removing history cannot authorize a new Redo.

Both repositories’ saved-move screens implement Redo after Undo. The existing Mac window history and mobile task-menu history own newly confirmed actions; an inverse is installed synchronously before awaiting the network. Actions that finish after a workspace change do not acquire history in the new account. The scoped feedback updates an open recovery screen and the ordinary task-list confirmation.

The normal-use migration/transfer gates remain disabled. The test hosts alone enable them, reusing their existing bundles, build products and Simulators. No service/schema deployment, provider registration or release configuration changes are included.

Field-edit and other hierarchy Redo, consistent shared activity history, older-data/history mapping, shared file/discussion custody and the wider migration acceptance still remain. Physical/provider/release/rollout deferrals are unchanged.

Current verification and exact limitations are recorded in verification.json; native peers are synthetic HTTP services and do not establish genuine shared-account or hosted SQL acceptance.

Both full apps build and pass strict signature verification. iPhone largest-text saved Redo/cold return, ordinary iPhone task-menu Undo → Redo → Undo, and iPad largest-text saved Redo/cold return each pass one actual UI journey. Every peer ends with exactly four distinct requests/four writes, exact source/nested fields, an empty destination and the untouched sibling at version 1.

Mac keyboard/runtime acceptance remains open: computer use reports the Mac locked. No Mac keyboard success, genuine shared-account/cloud acceptance, VoiceOver listening or hosted SQL rerun is claimed by these mobile results. The current normal migration/transfer flags stay off.
