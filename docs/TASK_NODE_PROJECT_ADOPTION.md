# Child history in reviewed project transfers

26 October 2026. Prepared migration `20261026121332_task_node_project_adoption_review.sql` and both owned clients include
child history in project-adoption review. This is locally verified review
coverage, not complete historical custody or hosted rollout acceptance.

## What changes

The bounded contents snapshot adds `task_node_activity`: count, serialized-byte
budget and deterministic row fingerprints. Selection matches parent history:
current roots in the selected branches, or before/after project references.
Deleted roots and moved-out historical intervals participate without duplicating
rows. Titles, notes, state documents and private hashes stay out of the response.
The existing 100,000 total-record and 32 MiB review limits include these rows.

The participant cohort includes child creators and actors, preserving the current
Auth/session/connection/account locking order. Child rows are locked with the
same nonblocking row-lock rule as parent history. The existing realm-write
trigger is extended to the child table, so child edit/revert changes its monotonic
epoch, and late writes cannot commit through a project-ownership fence. The
original connection pause, task authority, team role and attachment rules remain.

A versioned `child_history_protocol: 1` response requires exactly the additional
count category. Current clients still read legacy responses with their original
exact keys. Unknown versions, missing/unversioned categories, fractional/negative
counts and aggregate overflow fail validation. Older clients' strict category
sets reject the extended response. Pending approvals made before this upgrade
become stale through the changed contents proof, even if the new count is zero.
Existing applied receipts and saved-command shapes remain unchanged.

The native review adds Task history entries and Subtask history entries. Review
and commit responses must agree exactly. The SQL preserves existing function
ACLs, including the authenticated execution path required by the existing public
invoker wrapper. No new public API, rollout flag or client ledger write is added.
The first fixture attempt incorrectly revoked that existing private review path;
it failed with 42501, was corrected, and is not counted as acceptance.

## Remaining service and product work

The existing adoption registry binds current root tasks, not historical events.
A deleted root's history can be counted/fingerprinted while still lacking team
custody; a moved-out root must not be assigned wholesale to the destination team.
This affects parent history too. An event/interval custody design, removal/read
rules and author-removal/team-deletion acceptance are still needed before rollout.
The report records the actual post-transfer registry observation separately from
passing review checks. This milestone does not claim that those histories survive
later author removal, nor silently grant access to another personal project.

After historical custody, combine parent/child activity with independent sequences,
stable occurrences, work eligibility and explicit coverage; connect activity,
Insights and Project pulse/widget output. Broader calendar periods, heading
creation/conversion/race/largest-text/spoken checks, installed widgets and
cross-device/provider adapters remain open. Normal heading authoring and hosted
configuration remain unchanged. All user-deferred release/provider gates stay
pending; the full Px goal remains active.
