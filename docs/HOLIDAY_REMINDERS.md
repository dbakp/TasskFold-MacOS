# Reviewed holiday reminders

This rank-5 capability applies to one independent calendar reminder. It does not move a task's plan, change other reminder settings, infer a country from a device, subscribe to a private calendar or enable remote delivery.

In a repeating reminder, open **Add holiday policy**. **Country calendar** is the default source: choose a country to fetch its public holidays automatically for the selected year. Where the provider reports regional public holidays, choose **Nationwide only** or an ISO 3166-2 region code. A selected region includes national dates as well as its own. Search covers provider country names and codes; no device-country guess is made. Review the dates, choose **Skip alert** or **Move to next available day**, and confirm coverage before Apply. Apply returns to the upcoming-alert preview. Done still uses the existing task Save/autosave and Undo contract; Cancel discards the draft.

**Calendar file** is a secondary source for company or other calendars: import an all-day iCalendar (.ics) file, enter its name and region/organization, and review coverage. **Use ordinary calendar dates** removes only this policy from the reminder draft.

Calendar reminders keep their saved time zone when travelling. Each imported date is a civil date in that zone. Saturday/Sunday avoidance is a separate explicit option, default Off; it is not guessed from the region. Source fields remain labelled after entry, long content uses native scrolling, and the iOS file browser has an app-owned accessible Cancel action.

## Finite source and update policy

Both sources produce a snapshot for one explicitly reviewed Gregorian year. Country/year selection automatically fetches data; **Refresh holiday dates** fetches a new draft for review. Regional selection filters the fetched response locally. Saved alerts use reviewed dates offline and do not depend on a later request succeeding. Changing source/year/country invalidates prior in-flight work and requires a fresh coverage review. Source-switching cannot reuse the previous source’s dates. The file-name suggestion does not overwrite a name edited while reading.

Alerts under this policy are scheduled only within the reviewed year. An ongoing rule asks for another review after source coverage expires; an ended rule stays ended. There is no silent subscription or inferred next-year calendar. Empty coverage also needs explicit review. Only reviewed dates, source name, region, year, digest, optional country/provider/region-code provenance and policy choices are saved with the task. People who can read that task can read those settings. Review-only holiday names and original provider/file contents are excluded, along with notes, links, attendees, UIDs and filenames.

### Automatic country provider

The adapter uses [Nager.Holidays Community API v4](https://nagerholidays.com/api), following its [current OpenAPI contract](https://nagerholidays.com/openapi/community-v4.json): `Countries/Available` and `Holidays/{countryCode}/{year}`. It accepts only entries classified **Public**. School, bank-only, authority, optional and observance entries do not become excluded days. Nationwide scope excludes regional-only entries; regional scope includes exactly the selected subdivision plus nationwide entries. The provider covers first-level subdivisions, not city/company closures, and some locally announced holidays may be missing; the UI makes those limits visible. Regional codes come from that year’s Public entries, so this is not a complete directory of every administrative region.

Requests use a fixed HTTPS host, explicit validated country/year, no authorization or task content, an ephemeral cookie/credential-free session, no redirects, 25-second request/30-second resource limits and a streamed 1 MB response cap. HTTP failures, unsupported types, malformed dates, country/year mismatches and invalid regional scope refuse the entire new snapshot. Errors preserve saved settings and offer retry or file import. Countries are bounded to 300 unique codes; holiday responses to 1,000 entries and 300 regional codes per entry. The SHA-256 digest records the source response; alert semantics depend on the reviewed dates, not response formatting.

**Release dependency:** [provider terms](https://nagerholidays.com/legal/termsofservice) require active sponsorship for commercial use. Sponsorship has not been purchased or confirmed. This implementation does not resolve that release requirement or promise provider availability/official completeness. API v4 is selected because the provider’s documented v3 retirement is January 2027. No provider account, secret, purchase, backend mutation or private-calendar connection was created.

## Scheduling and response rules

Skip consumes an original calendar occurrence without creating an alert. A skipped occurrence still uses the calendar rule's count. Move retains the saved wall clock on the next date not excluded by the snapshot or optional weekend choice. It also skips an unavailable civil date, using the existing gap/fold resolver for the chosen clock. Alerts arriving at the same instant coalesce. They never move beyond the repeat rule's inclusive end or the snapshot's year. The count remains a limit on original slots, not a guarantee of that many distinct delivered alerts.

An occurrence is emitted only in the future, without catch-up alerts. Seeking includes the preceding excluded run so a moved alert is not lost after sleep. Work and output are bounded; native requests still share the existing 60-alert budget. Completing, deleting, disabling or losing access to a task uses the existing cancellation path. Independent calendar schedules on task successors keep the original anchor/count/policy; an old notification cannot target a successor.

The normal policy spec uses version 5, kind recurring, local-only channels and a version-1 `holiday_policy`. Its validated calendar fields remain the established Gregorian schedule contract. The policy contains `year`, sorted unique `dates`, `source`, `region`, `digest`, `mode` (skip/next-day) and `avoid_weekends`, with optional validated `origin` (`provider: nager-v4`, country and optional subdivision). Date count is at most 366; name/region each at most 160 characters. Unsupported versions/malformed data remain opaque, with no substitute planned-time alert. Known policy edits retain unknown extension fields. Removing the policy restores version 2 and clears its policy field.

An existing Time Sensitive choice can wrap schedule version 5 in its version-4 envelope; its separate device/system allowance and normal fallback still apply. `r8` signatures bind the underlying calendar schedule, holiday timing choices, reviewed dates/year, original alert instant and task generation/completion revision. An elevated choice wraps that signature with the existing `r7` presentation signature. Source labels and file formatting do not alter scheduling semantics. Changed timing policy invalidates old action receipts, including snooze; exact shifted instants are validated against the current policy rather than the unadjusted calendar. Both versions remain local-only during delivery-authority handoffs.

## File support and bounds

Reads are security scoped, file coordinated and off the interface thread, with a known-size preflight and a 1 MB + one rejection-byte cap. Closing/replacing a review or changing its year invalidates late work. iOS handoff reuses the existing picker session transaction: selection and dismissal can arrive in either order, deliver once and cannot be consumed by a newer request. Workspace/task/reminder-row checks at the parent editor remain required before applying a saved spec.

The importer accepts complete published iCalendar 2.0 event files, UTF-8 including BOM/byte-folded text, all-day DTSTART, exclusive DTEND or whole-day/week DURATION, RDATE/EXDATE and cancelled events. Supported recurrence is DAILY/WEEKLY/MONTHLY/YEARLY with bounded INTERVAL, COUNT or date-only UNTIL, BYMONTH, BYMONTHDAY and BYDAY; monthly/yearly BYSETPOS operates on complete periods before count/end filtering. Weekly WKST is Monday. Ordinal yearly weekdays require BYMONTH. Nonmatching DTSTART rules, unsupported recurrence fields/overrides, duplicate UIDs, tentative/timed events and malformed dates fail the entire review rather than silently omitting holidays. Export an expanded all-day calendar for unsupported rule forms. No event alarm, attachment or URL is executed or fetched.

Bounds are 30,000 properties, 16 KiB per unfolded property, nesting depth 8, 4,000 events, 366 days per event, 16 distinct review names per date and 2,000,000 recurrence-expansion steps. Holiday descriptions are bounded display text; accepted calendar timezone components do not override the reminder's saved zone. These are Taskfold's reviewed-import limits, not a claim to support every iCalendar producer.

The iCalendar date, recurrence and exclusive-end conventions are based on [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545). No external holiday provider or Calendar permission is required for this import.
