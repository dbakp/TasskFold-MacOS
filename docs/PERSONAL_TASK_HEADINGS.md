# Personal cloud task headings

26 October 2026. Both independently owned apps now separate personal heading
compatibility from team access. The existing client opt-in remains absent from
normal app configuration; this source stage does not enable hosted rollout.

## Admission and delivery

An opted-in signed-in personal workspace can author headings only with an exact
`personal_task_types_protocol: 1` boundary for its current account and backend
origin. Local authoring keeps its existing opt-in. Missing, malformed or future
protocols cannot grant authoring. Shared editors and final shared mutations still
require their own captured team edit/lifecycle capabilities and live access;
the personal marker does not grant a team fallback.

The existing native root/nested editor, personal workflow/duplicate/restore and
reviewed import admission now share that personal compatibility check. It never
reinterprets literal titles. Existing metadata editing and deletion stay available
independently. Source-level admission is broader than this stage's root native
acceptance; wider nested/workflow/import/restore runtime remains open.

Before delivery, sync fetches a fresh boundary and pauses personal type-bearing
intentions when support is absent. Typed pending work forbids legacy-service
fallback. Root column writes (including explicit false/null) require compatible
schema; nested transitions use their captured tree baseline, not the optimistic
already-converted row. Ordinary metadata changes keep their ordinary writer.

Compatibility is deliberately distinct from lost access: a pause does not
quarantine the queue, hide the offline edit, erase Undo history or require an
access-recovery backup. Normal workspace refresh retains the pending intention
and overlays it on the fetched source. The current queue and message remain
visible; restored support can deliver that exact intention on refresh/relaunch.
A delivery error retains the original intention for the next refresh rather than
assuming that no server write occurred. Existing completion revisions, task
generations and baseline merge still govern type changes and immediate retries.

## Service contract

The source-only migration adds the marker to the existing authenticated private
workspace boundary before its HMAC is computed. It introduces no writer, table,
public helper or new grant. It refuses installation if the heading column or
active heading invariant trigger is missing. The private boundary retains its
existing active-session checks, project access serialization and ACLs. Personal
compatibility can be advertised while all team authoring/read switches stay off.
This marker is a compatibility signal, not additional permission to edit rows.

Each repo passes 119 selected Core cases and 36 actual-role isolated PostgreSQL
checks. These cover exact client/account/origin gating, cold queue preservation,
separate access and delivery decisions, missing/future compatibility and no team
authority. SQL verifies partial-install refusal, HMAC stability/change, unchanged
RLS and function grants, account/session/anonymous boundaries, actual heading
insert/convert/inverse, lost-reply retry, stale ABA refusal, productive child
completion and legacy heading-completion refusal. Advisors report no new
warning/error findings beyond the existing fixture auth-init-plan allowance.

Native results, source bindings and exact limits are recorded in
`personal-task-headings/acceptance.json`. The reserved signed debug peer drives
actual Store sync, durable queues and Backend requests; all HTTP is intercepted
locally. Real SQL acceptance is independent. This is not genuine hosted Auth,
PostgREST paired-device, provider or distribution acceptance. Normal flags and
hosted configuration remain unchanged; older-client rollout, remote reminders,
release signing/distribution and the other user deferrals remain deferred.

## Permission-prompt follow-up

The user accidentally allowed the earlier Mac local-network request. Its old
entry did not appear in System Settings after refresh and registering the current
isolated host, so that grant was not reset. A fresh disposable **Taskfold Network
Permission Test** identity requested the permission and the user confirmed choosing
**Don't Allow**. This verifies that fresh test identity's denial only. It loads
no Taskfold accounts or tasks; it was stopped after the check. Other apps' privacy
settings were left unchanged. Heading acceptance uses the local HTTP peer and
does not rely on that local-network grant or print any job.

## Installed acceptance result

Three final scenarios pass independently on each signed Mac/iPhone/iPad host:
(1) lost response, cold pause under missing support, restored support and exact
retry with one type transition; (2) support removed before Save/autosave, zero
requests, a visible preserved cold queue, then one original write after recovery;
(3) missing support hides type controls while ordinary editing still persists.
Titles, full notes, child rows, generation, account/project and opaque fields stay
unchanged through the typed retry. Personal requests contain no team scope.

Initial failures were test-driver issues: a lost reply correctly stops sync, so
the new boundary is observed on the next cold refresh; the Mac runner cannot
rewrite the host's protected fixture file, so app-owned debug controls now change
the synthetic provider state. These controls require the exact reserved host and
explicit personal-test flag. Initial results remain separate from final passes.
The native peer is not a substitute for hosted Auth/RLS or cross-device acceptance.
Phone/tablet images show the test wrapper after confirmation, not a full editor
layout audit. The Mac inspector image is clear; wider spoken, largest-text, nested,
new-task/workflow/import/restore and personal Undo/Redo runtime remain open.
