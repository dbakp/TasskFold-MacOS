# Child completion recovery: terminal decision and safe replacement

An uncertain completion can now be resolved using its exact saved request. If it already applied, the service returns its original validated receipt. Otherwise it permanently closes that actor/request identity before the app may save a fresh replacement. Resolution itself never edits task content. Ordinary Store/UI flows and server feature gates remain unchanged.

The canonical migration is `20261029215232_child_task_completion_resolution.sql`, generated by the Supabase CLI after direct isolated execution and advisor checks. Each repository owns its copy; the migration identity and SQL bytes agree. Nothing was deployed to the hosted service.

## Server guarantees

- Metadata-only resolution needs the live confirmed account/session and exact bounded original body. It reads no task content and remains available after edit gates, task/project access or the task itself are gone. A recovered applied proof includes only the original completion cohort/identities, never a task title, notes, files or unrelated fields.
- Closed fingerprints and applied receipts are permanent for that account; no expiration turns an old UUID into fresh mutation authority. Changed bodies cannot reuse the decision. Actor namespaces are isolated, new closures are bounded to 2,000/day, and known closures/applied results bypass the new-closure quota.
- Complete/Reopen/Undo refuse closed identities before task reads, with a final receipt fence as defense in depth. Field preparation/receipts/closure and shared team task edit/batch receipts also refuse the closed identity.
- Existing child operations serialize with closure on the actor lock. Legacy team writers take root locks before their final receipts, so the new actor/request fence uses **nonblocking** advisory locks at that late point. A busy decision aborts the whole ordinary statement; a committed closure refuses it. This avoids introducing the reverse actor/root lock order.
- Tests pause an actual legacy team command after its root update but before its receipt, commit the closure while that root is locked, then prove the late command rolls back its distinct title change and history. Both completion-first and close-first actual lock graphs are also exercised.
- New private rows have RLS, revoked direct role access and indexed budgets/actor-request checks. The public wrapper remains an invoker; privileged helpers have fixed search paths and live session admission. Existing task read/write policies are not widened.

These fences apply to the named nonce-bearing task protocols. They do not establish safe rollout against every older generic writer; the previously deferred old-client upgrade work remains deferred.

## Client recovery

- Strict terminal envelopes bind literal request, account, root/project/generation, child identity, action and original Undo reference. Applied decisions must also pass the existing full receipt validator. Unknown/duplicate keys, changed identities and invalid embedded receipts cannot authorize recovery or replacement.
- The encrypted journal now supports a validated `closed` phase. Previous three-field entry archives still decode. Attempted state is durable before a possibly lost close reply; a lost reply or proof-write failure keeps the original uncertain request.
- Closure must be durably saved before `replaceClosed` can append a fresh UUID. It cannot change target/action, reuse an identity, coalesce another window’s pending intent or replace an already applied result. A closed Undo may be replaced by a fresh Undo only against its same confirmed parent proof.
- Closed requests cannot be re-enqueued, sent or confirmed. Other pending identities can be resolved independently, but a replacement still cannot jump over another saved pending intent for that target.
- A fresh current account/server/session/access lease is required for metadata calls, while task-write admission is not. Cached terminal proofs avoid unnecessary network calls. Late success and failure are suppressed after departure. Transport uses the exact original body, no cookies/cache, redirect refusal, a 16 KiB response cap and sanitized failures.

Resolution is an explicit review/cancellation decision for unapplied work, not the automatic retry operation. Normal retry continues to send the same immutable request. Future UI wiring must make that difference clear and refresh the actual task after an applied result; a historical receipt is not a fresh task snapshot.
