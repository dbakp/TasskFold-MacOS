# Native recording publication and cold recovery

Reviewed 5 November 2026. The actual iPhone app data engine passes **17 checks** through genuine disposable Auth, REST, database and Storage services. The Mac current-source app compiles and passes strict signature verification; its native run is **not accepted** because the locked Mac blocked private test-container IO. Normal recording entry points remain disabled. No daily-use app was replaced.

## Accepted iPhone scope

The existing reserved Simulator app uses actual Store sign-in/sync, AAC decoding, private file vault, publication disk/actor, production AudioCommentPublicationFlow and Backend transport. Five separately terminated/launched processes create the original draft, reject an unrelated valid CA, save audience approval and lose a genuinely committed publication response, confirm that same original operation on cold return and download the exact clip, then reopen the confirmed journal offline without requests. Exactly one Storage object/upload and one publication exist; canonical unrelated task data stay exact. Source and service hashes bind the current owning code before/after the run.

The actual draft file's original/final SHA-256 values agree. App phase `sourceFingerprint` is a diagnostic hash of a *re-encoded binary plist* and can vary with dictionary order across processes; it is not the disk-byte preservation oracle. The separate driver `originalDraftDiskSHA256` / `finalDraftDiskSHA256` values are that oracle.

Only the audio forwarding connection uses the task-owned CA and separately signed valid localhost certificate, evaluated by native SecTrust/URLSession with exact host/port and explicit anchors. The negative unrelated-CA check refuses before handler Auth access. Existing Auth/REST forwarding still uses the isolated HTTP loopback gateway. No system CA, normal trust policy or normal session setting changes. This is scoped local TLS acceptance, not public Internet/release trust or hosted S3 acceptance.

The session is restored from a private synthetic test file, not Keychain. Invocation is programmatic inside the real app; it does not establish interactive controls, speech, live microphone recording or native project-adoption GUI/lifecycle acceptance. Broader shared/access-loss/account/window histories, mixed/legacy recording custody, other realm directions and hosted providers remain open. The previously accepted 49 service transfer checks per repo are retained without repeating that unchanged matrix.

## Mac and resource cleanup

The native Mac attempt stalled before any accepted phase. After verifying process commands, exact container labels and nonce/account ownership, all five owned containers, internal network, handler and private temporary TLS directory were removed. The isolated app/driver were stopped. A few tiny synthetic files in the reserved Mac sandbox remain pending access; their exact paths and nonce are in `mac-blocked-cleanup.json`. Never delete the entire sandbox or bypass permissions. The runner now bounds protected file operations and closes services before private-file cleanup, recording any remaining paths.

The final iPhone run closed its app/handler, removed all its owned services/private files and restored the Simulator to Shutdown. End-of-run storage is about 60.4 GiB free; the two reusable selected compiler caches remain below 768 MiB each. The cleanup budget now includes explicit SDK modules and compilation CAS; eight meaningful file-safety/budget tests pass independently in each repo. No real data, Keychain items, Docker user volumes or unrelated devices were deleted. Cache cleanup reports zero removals because the retained caches are healthy and bounded.

The initial harness attempts caught an OpenSSL flag typo, a driver declaration-order error and a missing isolated Mac Info.plist. These were corrected before the accepted phone run/current Mac build. They are infrastructure failures, not product passes. The raw blocked Mac attempt required verified external cleanup; the hardened cleanup path has a passing phone run, but the locked Mac timeout path is not itself accepted.
