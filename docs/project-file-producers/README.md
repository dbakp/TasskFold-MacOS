# Recover interrupted project-copy producers · 6 November 2026

A trusted file-copy handler now owns a fresh private producer identity before requesting an upload reservation. Only a newly created upload ticket is bound to that producer. A read-only verifier never acquires another producer’s ticket. The native preparation API, plan/consent/receipt shapes and existing atomic project move remain unchanged; no Swift app, normal gate or hosted configuration changed.

If the reservation response is lost before any POST was issued, a bounded independent service observation can settle that producer’s ticket. A closed identity also blocks a delayed reservation from creating a later upload grant. An observed successful/conflicting provider response can attest terminal transport, even if later byte verification fails. Fully read and hashed committed bytes retain the existing positive reconciliation path. A cancelled preparation can then pass through existing fenced Storage maintenance; settlement alone never certifies deletion or releases the charged bytes.

Producer observations are service-only. Clients cannot supply producer IDs or call terminal observations. Private rows have RLS and no direct client/service table grants. An observation remains available after logout, access departure or gate pause because it concerns a previously bound producer; it cannot authorize a new copy or transfer. Matching actor/plan/operation identities, exact proof type, immutable closed proofs and plan → item → operation → writer lock ordering fence the transaction. All provider byte writes/deletes remain in the Storage API, consistent with [Supabase’s Storage schema guidance](https://supabase.com/docs/guides/storage/schema/design).

An issued POST with an unknown outcome is deliberately left open. Missing metadata, a timeout or elapsed time cannot stand in for terminal proof. The fixture actually delivers one delayed upload after cancellation: maintenance retains its charge while absent, then verifies its eventual bytes before settling and deleting it. If an Edge process dies without a terminal observation and no positive provider bytes appear, the unresolved writer still remains a gap. This milestone does not claim complete process-death recovery, legacy-writer settlement, hosted S3/Edge acceptance, broader account-removal/retention or mixed-policy/native adoption acceptance.
