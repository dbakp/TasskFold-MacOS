# Genuine native conflict refusal and reviewed replacement

Reviewed 3 November 2026. The actual owning app passes 18 field-conflict and 18 hierarchy-conflict checks across ten separate processes. Both use the production Store-created presentation/recovery model, encrypted journal, sender, review/replacement construction and Backend against genuine local Auth/REST with every owning migration replayed. No ordinary app gate, hosted service or release configuration changed. Field review now joins an existing workspace sync before constructing its comparison, rather than treating sync’s busy early return as fresh data; hierarchy reads share the same preflight through the retained wrapper.

## Two bounded competing-edit cases

**Fields:** Save an offline child request touching description and priority. While the app is closed, another real API request changes both those fields and the sibling/root titles. The cold old request must be refused as needing review, remain attempted with its original body/baseline and have no confirmation. The remote tree must remain unchanged. After another cold launch, explicitly close the original through the actual metadata-only service and retain its closure proof. Refresh the actual Store as the normal review screen does, read the genuine current values and construct the real comparison and select only Description. Save its fresh request offline; the new command must omit Priority and capture the current description as its baseline. No edit is sent during that save. A real workspace response is held before delivery while a background Store sync is active; the normal read preflight must register the join and remain unfinished until release, then compare the refreshed cache. The compiled field-review view now calls that same preflight. Cold send confirms the fresh identity, then an offline restart retains both the original closed history and the new confirmation/cache. The remote priority 1 and other remote work survive; only the selected local description replaces its remote counterpart.

**Hierarchy:** Save an offline whole-branch move, including a nested descendant. Another real action reorders the roots and edits the destination/root titles. Cold send of the stale structure version must be refused for review without changing that competing tree. Cold reopen, explicitly stop the old action through the genuine close endpoint and retain the closure proof. Run the normal hierarchy-read synchronization, read current hierarchy and use the actual fresh-review builder, and save a new queued move offline against that current version. The server is still unchanged until a later cold send. Another offline restart retains original closure, fresh confirmation and the merged Store/cache. Exactly three original unique nodes survive. Only the competitor's reorder and reviewed move advance the structure version; refused and closed old actions do not.

The five processes per case are queue, refuse, review/save, send and offline verify. Original action/baseline fingerprints remain unchanged throughout (only the semantically unordered baseline field-name Set is sorted; authored arrays and values stay exact); fresh identities and terminal closure proofs survive cold return. Driver comparisons verify exact expected cache/server trees, untouched root description/generation, retained record authority, no ordinary root mutation queue and no send during offline review save.

## Limits and reproduction

Review choices are programmatic invocations of the actual production controllers; this is not a visual/keyboard/VoiceOver walkthrough of the comparison screens. These cases do not establish every conflict kind, changed incarnation, archive, access revocation, shared-account/window/background race or legacy migration. Existing root/field/whole-branch lost-reply and cold Undo/Redo evidence is retained separately.

Read/write switches are enabled only in the reserved isolated build and disposable local database. The existing test-only transport forwards real local replies (the busy-read check briefly holds a real response; it supplies no fabricated data); the disposable nonce/account key exercises actual encrypted I/O without accepting protected Keychain access. Genuine issued sessions use the existing private test file. TLS/release session handling and pg_net placement remain separate. No provider/hosted mutation or normal rollout was enabled.

With current signed isolated products, run `node Scripts/Database/test-native-store-sync.mjs mac /tmp/taskfold-native-field-conflict-<unique>.json field-conflict`, then the analogous command with `structure-conflict`. The existing 20 GiB floor, owning-source/signature checks, scoped process cleanup and disposable service ownership guards apply. Apps/services are closed and the initial iPhone Simulator state restored after each run; disposable credentials/configuration are removed.
