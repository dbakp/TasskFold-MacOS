# Reuse unchanged rows containing exact preserved JSON

The large synthetic workspace was falling back to whole-workspace encoding because prepared rows rejected every opaque JSON leaf. These leaves preserve imported large numbers and objects with Unicode-distinct keys. Both app owners now prepare them with the existing preserving codec, validate the completed substituted row at the conservative 508-level envelope allowance, and reuse only the exact immutable authored row at its original ordinal. A changed row is fully re-encoded and checked. No ID/equality shortcut, file-format or rollout change. The immediate field writer remains available while rows prepare; selecting it no longer disables the first background request. Explicit row decline/failure still disables retries until reset.

Existing byte/row/table-name/header/metadata limits, source-scoped adoption, cancellation, external-file replacement and ordinary-writer fallback stay in place. The completed row scan includes the full nested opaque leaf; its independently valid depth cannot certify the enclosing snapshot. Invalid numbers/depth continue to fail as before. If optimization admission fails, the existing ordinary writer decides the result. No partial cache publishes on a failed encoding.

The first actual app candidate refused to claim success because no rows had prepared. That exposed the immediate field-writer handoff, fixed with an encode-before-request regression case. The rejected report and its source/image manifest are retained.

Each owner passes 134 selected Core cases (Mac also records one optional skip). The revised opaque-row case checks exact decimal/large-exponent/signed-zero/nested Unicode-object bytes through current edits, reused siblings, reconstruction and fresh decode. Three additional cases exercise the encode-before-request field-writer handoff, explicit row-preparation control and opaque depth boundaries against the whole-envelope reference. Existing stale/cancelled/external-source, failed-write rollback, duplicate/missing-ID/reorder, invalid-number, metadata/header and budget cases remain. Both signed SDK builds bind the complete owning/prepared source manifests to their exact code images and verify real development-team signatures.

The reserved iPhone Store fixture now yields to queued startup work in both modes and awaits its existing guarded background worker outside measured saves. This corrects the previous synchronous fixture, which never let that worker run. The comparison uses two sequential mode runs of one identical executable and source manifest (mode order is not counterbalanced): its DEBUG-only control disables only prepared rows, keeping the same codec/read/metadata policies. The normal app keeps preparation enabled. Ten actual Save calls per mode counterbalance cold/warm widget hashes; each save verifies exact durable work, untouched sibling and opaque fields, plus unchanged checkbox tokens. A separate cold launch checks all saved tables and widget states/tokens. In the candidate each measured save encodes two rows (three on the first save), including newly generated activity/settings work, and reuses 103–113 rows; the control reuses none. The full durable-state checks include the generated work.

Warm-hash Save medians are 28.623 ms without prepared rows and 26.334 ms with them; encoding is 14.355 ms and 10.411 ms respectively. These are synthetic Simulator API measurements, not visual smoothness, hardware frame rate or end-to-end UI acceptance. Older sync-harness numbers are not treated as a causal control for this updated harness. Broader navigation/render/library/account scope remains open.

The native driver preserves the original three fixture directories by file SHA and original absence, restores them after each run, removes only generated fixture work and stops its isolated process. Only the fixed owned phone is used and shut down if booted; no clones or real accounts/tasks are involved. Host Info settings and current signed products remain unchanged after owned-output cleanup. Both independent progress renderers pass with the existing checkpoint count; the responsiveness parent stays open. Normal Mac updates still await the existing Xcode/App Groups prerequisite, and phone installation remains deferred.
