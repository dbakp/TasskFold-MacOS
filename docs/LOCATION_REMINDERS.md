# Device-private location reminders

Status: rank-5 implementation and acceptance in progress. Normal iPhone/iPad Notifications now includes **Place reminders** setup, with explicit opt-in and private management. Task authoring is a preview on devices whose actual OS supports region monitoring; unsupported devices retain time reminders and can manage/revoke existing private setup. Permission, Precise Location, device consent and a saved task review still gate native preparation. Simulator authoring overrides and synthetic failure hooks retain a separate exact isolated DEBUG gate. Physical delivery/OS-origin callback acceptance, private desktop-to-phone authoring, broader accessibility and remaining P2 gates are open. This is not completed location-reminder or Px acceptance.

## Product behavior being implemented

Choose **Arrive** or **Leave** for one reviewed private place. The default is one alert on the next matching boundary crossing. **Every visit until completed** explicitly requests a native repeating boundary trigger while the same task remains open. Snoozing one visit creates a separate time alert and does not pause later visits. Save/Cancel use the existing task draft; choosing a place or pressing Done cannot arm an alert before the task is durably saved. A saved place has a name, a reviewed pin and a 100–5,000 metre radius; 250 metres is the initial draft choice. Coordinates use integer millionths of a degree. Boundary detection is approximate and may be delayed by iOS, hardware, permissions and system settings. There is no continuous location log or immediate-delivery guarantee. Arrive and Leave together are never inferred.

Use Apple's [UNLocationNotificationTrigger](https://developer.apple.com/documentation/usernotifications/unlocationnotificationtrigger) with the explicitly reviewed repeat flag. The system owns boundary detection and can notify without Taskfold tracking location in the background. Apple documents When In Use authorization for this trigger, rather than Always access. Native code must check actual availability and surface OS scheduling refusals. The app chooses a conservative maximum of 20 location alerts; this is not a promise that the OS will accept 20 triggers. The current Apple SDK explicitly excludes this trigger on macOS and Mac Catalyst. The Mac must preserve and explain the phone/tablet setting and support intentional removal; it must not request Mac location permission or reinterpret the reminder as a time alert.

### Places and consent

Saved place coordinates, radius and name remain inside the originating installation's account-scoped private storage. They must not enter task rows, widgets/App Groups, templates, share drafts, portable backups, task notification text or Taskfold backend requests. Deliberate Apple Maps/search use processes the viewed area/query with Apple as explained in the picker. Saving a reusable private place is a separate, clearly labelled action from saving a task reminder; cancelling a task must not leave an invisible armed notification. A place's pin/radius change creates a new opaque revision and requires affected reminders to be reviewed again. A rename alone retains the boundary revision.

The native implementation must provide reviewed map/search selection and optional **Use current location**. A map/address search sends the requested query to Apple's map service; it must be deliberate and explained. Current-location access is requested only after the user chooses it or enables location alerts. Use reduced-accuracy results honestly and allow pin correction. Apple documents that [reduced accuracy disables region monitoring](https://developer.apple.com/documentation/corelocation/cllocationmanager/accuracyauthorization); explain unavailable delivery and let the person choose Precise Location in Settings. Do not silently request temporary precise or Always authorization. Keep the existing notification permission/device-delivery choice separate, and add an explicit default-off location allowance for each account/device.

Private storage must use a dedicated Application Support directory, file protection, restricted file permissions, backup exclusion, bounded coordinated/atomic writes and a stable installation identity. Keep places until the person deletes them or the installation is removed; do not collect visit history. Account changes stop all owned location registrations and hide the other account's places. Returning to an account cannot silently revive a previously submitted/closed one-shot. Installation loss, restore or deleted private data requires new explicit setup. Missing and unreadable storage are different states: never replace a corrupt/unreadable journal with an apparently fresh one and begin registering alerts.

### Parity scope still open

The [current Todoist location guide](https://www.todoist.com/help/todoist/features/use-location-reminders-in-todoist-uGcwH2AJ6), checked on 22 October 2026, describes mobile Arrive/Leave alerts, address search, adjustable iOS radius, saved-location clearing and desktop/web authoring of mobile reminders. It does not specify a complete repeated-visit lifecycle contract. Taskfold must keep those authoring/management capabilities in its parity backlog; a handset-only one-shot implementation is not full location parity. Desktop-to-phone authoring needs a reviewed private handoff/account-only storage design so coordinates never leak into a shared task. That transport remains unimplemented; the current every-visit milestone is documented separately below. No Todoist account data was read or changed for this documentation check.

## Implemented private storage and picker

`LocationPlaceStore.swift` owns a bounded account-scoped placebook and stable installation journal under Application Support/Taskfold/LocationPrivate, outside shared data and portable task exports. It uses a backup-excluded 0700 directory, 0600 atomic files, iOS Complete Until First User Authentication protection, a process writer lock and bounded reads. Missing state stays missing until an explicit place save or device-consent grant; unreadable/future state is refused without replacement. Stale edits and journal rewinds are rejected. Confirmed whole-installation reset creates a fresh identity. Account-level clearing keeps other accounts and the notification journal.

The iOS component supports deliberate Apple address search, map-pin/map-center selection, a name, 100–5,000 metre radius, explicit Save/Cancel, edit/delete and confirmed clearing. Renaming retains the boundary revision; moving/resizing changes it. Optional current location creates a one-use manager and requests When In Use only after a tap, with cancellation and a 20-second timeout. Search has a separate 20-second timeout. Query and selected-area disclosure is visible. No Always/background location capability is added. Native simulator checks and filesystem evidence are recorded separately in `p2-location-place-storage-evidence.json`; simulator search and file checks do not prove physical protected-data behavior or genuine geofence delivery.

Current picker acceptance remains partial: iPhone search/save/relaunch/edit/delete and dark largest-text Cancel are exercised. The iPad keyboard-Search path now passes the full native save/relaunch/rename/radius/delete flow without changing task tables. Its selected-pin check explicitly scrolls the lazy form into view. iPad dark initial layout/Cancel also passes. Direct Search taps while typing remain unverified: automation does not invoke the action, system accessibility errors persist after a non-erasing simulator restart, and app-versus-simulator cause is unresolved. Borderless/plain styles and alternate scroll-dismissal behavior did not establish a fix; production behavior was retained.

This component remains behind an exact isolated debug route until public device-consent/permission controls, task save/cancel and native response handling are connected. Durable consent, combined admission and normal Store bootstrap are now implemented below. macOS owns the same private storage contract independently but has no location picker/permission UI. Private desktop-to-phone authoring remains open; current every-visit behavior is documented below.

## Native iOS adapter milestone

Arrival and departure use one reviewed circular boundary, one direction and the explicitly reviewed repeat flag. Notification content contains the task title and generic arrival/departure copy; the opaque receipt contains no place coordinates, radius or label. Inspection refuses time/missing/mode-mismatched/both-direction triggers, wrong identities/categories, fractional/off-grid geometry and unknown receipt fields. An observed changed boundary cannot match the desired candidate.

The adapter requires a current explicit allowance callback, checks region capability, existing When In Use/Always authorization, Precise Location, the device's maximum radius, notification authorization and free queue space. It never requests location permission or starts location updates. Typed refusal reasons support future UI. It rechecks allowance/cancellation around the OS add and scopes pending removal to location identifiers. Normal iOS refreshes now prune stale delivered alerts with a current-workspace check. The environment check reads settings only, not the user’s location. The adapter refuses before attempting a geofence add; this is **not positive OS registration or delivery acceptance**. The positive registration check is retained for a region-capable environment and explicitly skips where the system says unsupported. It is not included among passing Simulator cases. Permission/precision/radius gates beyond the unavailable-device branch, pending geofence registration/readback, native delivery and notification responses still require capable-device acceptance. The native fixture is restricted to DEBUG, the exact isolated workflow-test bundle and an extra argument. ## Private consent and normal iOS workspace lifecycle

The fixed private `LocationPrivate/state-v1.json` pathname now supports archive version 2 for a bounded explicit account-consent list. The journal and task-reference versions do not change. Existing version-1 archives load with consent off; an explicit grant/revoke atomically upgrades the private archive while preserving places, journal and installation identity. Consent never enters task snapshots or portable exports. Older private-store readers reject version 2 without replacing it. Unknown/future/malformed private data remains refused. A whole-installation reset clears all allowances and mints a fresh identity; stale device reviews cannot grant consent to that identity.

Normal iOS scheduling refreshes load this archive, install/reuse its journal engine and build a plan from currently accessible, unarchived tasks. Merely loading a synced or backed-up reference never prepares a new intent. Missing data creates no file/identity. Unreadable data fails closed and removes owned registrations without overwriting the file. The native allowance callback rereads private state and current task/place bindings before/around submission. Account-generation changes queue an empty desired state before further awaits; the scheduler also binds in-flight additions to the workspace incarnation so leave-and-return cannot authorize an old callback. Concurrent refresh callers wait for hydration and the latest admission pass before returning to notification actions.

The Store consent API checks the current workspace, separate reminder-delivery preference, native capability/location accuracy/permission and notification authorization. It never automatically requests permission or enables ordinary delivery. Disabling first suspends submissions and drains obsolete work, then saves the private choice. A failed save returns false, exposes the error and keeps alerts stopped for that session; it does not claim durable revocation. Public setup must explain retrying before closing when a choice could not be saved. Existing granted choices can be read on restart, but previously submitted/closed one-shots cannot silently rearm. Public consent/permission controls and task editing/action integration are still required before exposing the feature.

The isolated native lifecycle fixture uses the normal Store and real notification center to check missing-state bootstrap, unsupported-device grant refusal, private-consent hydration, concurrent refreshes, durable revocation, owned-orphan cleanup, unrelated-alert preservation, unreadable-file preservation and confirmed identity reset. Its synthetic raw consent/journal setup is test input, not proof of native permission acceptance or successful geofence registration. Task tables and pending mutations stay unchanged, and a subsequent launch keeps consent off. Exact scope and earlier harness failures are in `p2-location-workspace-evidence.json`.

## Reviewed task drafts and intent retirement

An iOS location reminder editor now supports explicit Arrive/Leave, selection from the private placebook, a map/area review, separate device allowance and Save/Cancel disclosure. Its permission helper requests When In Use only after a deliberate action, never starts location updates and never asks for Always access. Ordinary notification delivery remains a separate prerequisite. This editor and its task-write bridge are restricted to the exact isolated local DEBUG fixture while public setup and capable-device acceptance remain unfinished; normal app authoring stays hidden.

`LocationReminderReview` is a memory-only proposal, including the reviewed private boundary. Done changes only the parent task draft. It preserves opaque rows/extensions, materializes the existing implicit planned reminder, checks row limits and rejects duplicate boundaries, task/workspace/completion changes and moved/deleted pins. A rename with unchanged geometry remains usable. The task receives only the opaque version-6 one-shot or version-7 every-visit reference. The parent task Save uses its ordinary durable save/note-pin path first, then revalidates current data and prepares an intent only if this device's explicit allowance and native capability are currently valid. An unsupported/off device saves the reference unarmed with a review notice. Failed task persistence cannot create an armed intent. Asynchronous saves disable repeat taps and dismissal; stale workspace continuations cannot close another workspace's editor.

Normal iOS persistence now saves a bounded cancellation-only outbox **in the same atomic workspace snapshot replacement as the task change**. It compares the last durable cache with the proposed rows, covering local removal/replacement/disable/completion/deletion, Undo/Redo, synced changes and restore/recovery replacements. The outbox preserves earlier unacknowledged jobs even when a caller replaces the snapshot. It contains opaque ticket bindings, no place names, coordinates or radius; it is not a preparation/notification authority. Portable workspace exports exclude this top-level local metadata; account-bound encrypted recovery snapshots retain it so restoring a local safety copy cannot drop outstanding cancellation.

Location admission stays suppressed while cancellation is pending. After hydration, owned tickets are retired through the serialized engine and durable private journal; only then is their acknowledgement saved in the task cache. Process termination before the private write replays the outbox. Termination after that write but before acknowledgement harmlessly repeats retirement. Undo may restore the raw reference but cannot remove its outstanding cancellation or private revocation. An explicit cancelled tombstone is written even when retirement arrives before preparation; a late preparation with that nonce is refused. A task-cache refusal before atomic replacement saves neither the task change nor its new cancellation; a failed journal/acknowledgement write keeps the job for retry on refresh/relaunch. Full queues refuse further required cancellations instead of dropping existing jobs.

A readable missing private archive creates no identity and cannot authorize old alerts; jobs for an absent/replaced installation can be acknowledged without recreating private state. Unreadable private authority is never treated as missing: its jobs remain pending and location submissions stay suppressed. Account-generation checks fence acknowledgement after async retirement, so a response from the previous workspace cannot edit the newly opened cache. The independently owned Mac model reads/preserves the optional outbox and validates its bounds, but does not gain a native location engine or generate/consume iOS jobs. This is process-termination recovery using the existing atomic task-cache writer, not new hardware power-loss or filesystem-corruption acceptance. See `p2-location-retirement-outbox-evidence.json` for exact tests and remaining limits.

The private journal adds version 2 with a bounded monotonic `revoked` identifier list. It retains immutable closed entries and can revoke even an already-delivered receipt without rewriting history. Revoked entries must be closed; unknown IDs, duplicate IDs, rewind and revocation removal are refused. No coordinates, place names or visit timestamps are added. Journal version 1 still loads. Older private readers reject the new nested fields without replacement. Task-reference and notification-receipt formats are unchanged. The existing protected pathname and backup exclusion remain.

The iOS row distinguishes unsaved draft, another device, changed place, unreviewed, waiting, installed and ended/cancelled states from current private state. macOS independently recognizes arrival/departure references, explains the phone/tablet requirement, preserves their original fields and offers intentional deletion. It does not gain Mac location permission or a system trigger. Actual native Mac rendering/accessibility still needs acceptance. Native draft evidence and exact remaining gates are in `p2-location-task-drafts-evidence.json`.

## Proposed shared settings

Version 6, kind `location`, local-only channels and an explicit enabled Boolean wrap a version-1 `location_reference`. It contains only the originating device identity, original task ID/incarnation, private place ID/revision, one-shot arm nonce, Arrive/Leave choice and `repeats: false`. Taskfold's constructor writes no private geometry or place label. Unknown extensions survive supported settings toggles. The format remains opaque to `ReminderSpec`. Only the reviewed isolated local DEBUG bridge can author it; ordinary app authoring and backend writes from that bridge remain disabled.

A reference is bound to its original task identity/incarnation. Copying, templating, restoring with a new incarnation, or completing a recurring task cannot retarget it to a different task. Actual `TaskCompletion` successor creation preserves the opaque row but the proposed planner refuses its old binding. The new task needs its own reviewed location reminder. Changing a task's planned date does not move the private place or create a new location opportunity.

The native save path must keep the existing workspace generation, task identity/incarnation, accessible-record and reminder-collection checks. A private place cannot grant access to a task. The planner accepts only currently accessible, unarchived tasks supplied by the existing authorization path. Duplicate task identities, duplicate place identities within an account, duplicate reminder identities and oversized reminder collections are refused. Duplicate boundary/transition settings on the same task are detected independently of their random arm nonces.

## One-shot lifecycle

The journal is owned by one installation. Before a task can arm a new reference, an explicit setup action durably prepares its ticket. Merely syncing a setting, reading a backup or finding a matching private pin cannot prepare that intent. The engine serializes preparations with registration writes. Preparing an intent before task hydration does not inspect, add or remove OS notifications; an explicit current plan is required before reconciliation.

Before calling the OS, transition **prepared → reserved** and durably save. A successful registration transitions to **installed**. The receipt binds account, device, original task/incarnation, completion revision, setting identity, place identity/revision, arm nonce and transition. Private geometry and place name are absent from receipts and notification content. Titles are snapshots of the task when armed; a title edit alone must not resubmit a potentially fired geofence.

A matching pending registration can recover **reserved → installed** after a crash, without another OS submission. A submitted registration that is no longer pending becomes **closed**, even if the app cannot tell delivery from dismissal, permission loss or an OS removal. A reserved request with no pending proof closes as ambiguous. Refusal or a boundary mismatch closes without automatic retry. Another opportunity requires a deliberate new arm nonce. A genuine later OS response can still match an original delivered/missing/ambiguous reservation while its current task/place/account binding remains valid; cancelled, failed, untracked and never-submitted prepared entries cannot authorize actions. Native response-origin decoding, replay handling and task mutations are now connected as described below; a genuine OS boundary callback still needs capable-device acceptance.

The engine fences each asynchronous reconciliation. If an account/desired-state change arrives while persistence or OS registration is awaiting a result, the old context cannot proceed to a new submission; a late OS addition is removed. Unreadable journals fail closed and clear only the owned location namespace. Undecodable owned requests must be reported for removal; time/Focus notifications must remain untouched. No journal history is silently pruned: at 2,048 entries, new preparation is refused. A future explicit reset must mint a new installation identity so old references cannot be treated as fresh opportunities.

## Combined notification admission

The shared `ReminderScheduler` now serializes time, explicit snoozes, Focus and an optional location engine in one drain. Priority is Focus, explicit snoozes, up to 20 locations ordered by task priority/stable identity, then ordinary time alerts by fire date. Only matching durably prepared, nonclosed location intents reserve slots. Unknown, consumed and refused intents cannot starve valid waiting work. Pending requests outside the time/Focus decoder count against the same conservative 60-request budget, including when no location engine is installed.

Reconciliation first removes obsolete location registrations without new submissions, then removes excess time requests before adding within the remaining capacity, and finally submits locations. Refused or consumed one-shots release their reservation in that same drain. Unrelated pending identifiers are preserved. The native time adapter also checks the actual OS queue before adding; a full queue defers the request rather than claiming delivery. Focus and explicit snoozes retain priority on retry. A specific snooze reports its own scheduled/waiting/failed result, independently of other deferred requests. Ordinary time snoozes now persist never-submitted waiting intents and recover their exact chosen fire instant after restart, with reservation-before-submit and conservative ambiguous-outcome closure. Location snoozes keep their separate private-action ledger. See the current recovery section of `REMINDER_SNOOZE.md` and `p2-time-snooze-recovery-evidence.json` for scope; neither path promises submission while the app is closed and the OS queue is full.

Candidate-scoped callbacks fence account/plan changes before reservation, after persistence and after an OS add. A late obsolete addition is removed. Same-installation updates retain the active journal actor so an older snapshot cannot overwrite an in-flight reservation; an explicit installation identity change swaps engines only through this drain. Unchanged titles and new snoozes do not rearm an existing boundary. If priority/capacity removes a previously submitted one-shot, its journal closes as cancelled and another opportunity requires deliberate review/rearming.

The normal iOS Store now installs the engine and supplies a current plan only when its readable archive contains explicit device consent, ordinary reminder delivery is enabled and native location capability/authorization is valid. The reviewed task-write bridge can prepare explicit intents only through its exact isolated local DEBUG route; public location setup/editing remains hidden. macOS owns the shared model/store/admission code without requesting location permission or installing an unsupported system trigger. The shared-engine tests use a modeled common queue and check its peak after every mutation; they do not prove successful native mixed geofence/time admission. Native request-format, unsupported-device and actual time-capacity checks are recorded separately in `p2-notification-admission-evidence.json`. The Simulator still reports region monitoring unavailable, so positive native location registration, delivery and responses remain open.

The native decoder requires the ticket mode to match the trigger’s repeat flag. Mac preserves and describes the setting, without requesting location permission or scheduling location alerts. A matching pending repeating trigger remains installed after delivery; repeated observations neither resubmit it nor write passive visit history. Closed history remains immutable, and stale or skipped submission epochs are refused.

## Explicit ended-action cleanup — 22 October 2026

The experimental iOS reminder editor now has **Clear ended reminder history**, with a confirmation explaining that active reminders and tasks are kept. Cancel performs no write. The command rereads protected private storage, checks the captured account/workspace after the await, and uses the normal atomic task-cache writer. It filters both the latest durable ledger and the proposed ledger before their ordinary monotonic merge. A write refusal restores memory and preserves the durable cache for retry. It does not create a task command or change task rows, scheduled dates or pending commands.

Cleanup requires an exact account/device/ticket match in a valid private journal. Only permanently cancelled, failed, untracked or explicitly revoked closed intents qualify. The private tombstone remains immutable, so deleting its action receipts cannot authorize an old boundary or snooze response. Active repeat intents, prepared/reserved intents, delivered/missing/ambiguous one-shots that can still receive a response, unknown tickets and other accounts/installations keep their records. A normal save, Undo or task-cache restore cannot request deletion simply by omitting a receipt; only this explicit maintenance command supplies private authority.

The 2,048-action bound still fails closed. A full ledger of qualifying retired receipts can be cleared, making space for new actions. Active-repeat receipts are kept: reviewing and replacing that reminder first retires its old intent. Cleanup does not discard the private journal or make room in its separate 2,048-intent bound. ## Recoverable whole-device reset — 22 October 2026

The experimental Places screen offers **Reset place reminders** for healthy or unreadable setup. A standard alert names the scope: all place reminders and snoozes on this device stop, every account’s saved places and private consent are removed, task details and other reminder types are kept, and using location reminders again requires review and enablement. Cancel performs no reset. The task editor and place chooser both use the Store-coordinated command; standalone private-picker fixtures retain their direct storage reset. The chooser clears its selected pin after reset and revalidates a selection after dismissal, with a guard against overwriting a newer choice. The final build has a native picker Save/Cancel/relaunch regression; dedicated reset-from-open-draft acceptance remains open.

Explicit reset writes a fresh private installation identity with empty places/journal/consent and private archive version 3, `supersedesEarlierInstallations: true`. Legacy archives 1/2 still read without reset authority. Consent and place/journal edits preserve version 3 and its receipt. Malformed flags/future formats are refused. The receipt is outside task snapshots, widgets, shared rows and portable/encrypted task backups; no task or notification format changes. Selected previous committed private readers refuse the new archive without overwriting it on ordinary edits. This is selected-reader evidence, not the user-deferred general rollout work.

The private reset commits before action-cache cleanup. Only a valid current reset receipt may discard this account’s action records bound to other installation identities. Current-identity records and other-account records are retained. The cache writer holds the private writer lock from identity revalidation and directory synchronization through the atomic cache replacement, preventing a stale reset proof from deleting a newer installation’s receipts. Directory synchronization must succeed before deletion; this also settles an earlier uncertain rename acknowledgement. A failed cache save leaves the private reset in force and old receipts available for retry. Normal workspace hydration uses that durable receipt to finish cleanup after process termination, or after old task-cache recovery reintroduces earlier receipts. Each account’s cache is handled when that workspace opens; other accounts’ cache files are not opened by this command.

Reset removes owned location and location-snooze requests/delivered content. Ordinary time and Focus namespaces are preserved. Old task references remain saved for review, but cannot authorize an alert under the fresh identity. The UI explains the local reset and need to review the place. Reset never grants permissions or silently re-arms a restored row. It recovers both the private journal’s 2,048-intent capacity and old-installation action capacity; clearing just known ended actions remains the less disruptive option. Current active-reminder history is not automatically pruned by age.

The isolated iPhone/iPad test saves a real native time snooze, adds another synthetic account’s private place/consent, checks reset Cancel, holds the process after the private reset and an injected cache-write refusal, then relaunches without the hold. It verifies durable cache recovery, unchanged task rows, empty private setup/consent, preserved unrelated native time requests, removed old snoozes and rejected old callback inputs. Core tests separately cover a full ledger, stale proof/private writer-lock races, failed cache write/relaunch, other-account/current-device preservation and invalid formats. These establish process-loss recovery under the app’s filesystem contract; they do not establish hardware power-loss durability, physical protected-data recovery, genuine geofence/OS-origin delivery or native account-switch acceptance of this new reset bridge.

Evidence is in `p2-location-reset-evidence.json`.
