# Completion history and recovery follow-up — 30 October 2026

The normal completion flow no longer requires manually clearing old confirmations after 64 actions. The journal makes room atomically with the incoming operation, removing only the oldest entirely confirmed families. An original action and all its Undo records stay together. Any queued, attempted or stopped member protects its entire family; the operation being confirmed is also protected.

The journal retains its existing version-1 format, encryption, 64-record and 2,100,000-byte JSON limits, account/process locks and removal tombstone. First acknowledgement moves a confirmed entry to the end without reordering pending work. Pruning never changes the server, a task, an immutable request body or an uncertain outcome. Validation, encryption/write failure and cancellation cannot persist a partially pruned archive. If protected work fills the journal, a specific review message appears before another request can be sent.

The recovery list now puts pending actions first (in their existing order), stopped actions next and recent confirmations last. Current subtask names are loaded once per distinct parent per live presentation revision, sequentially, instead of once for each action row. Account/backend/workspace/session/access, task generation/project and node incarnation guards still apply; names exist only in presentation memory. A successful Send/Undo from current-value review returns to the recovery list.
