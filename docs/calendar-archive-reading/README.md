# Reuse current archive inheritance in Calendar

CalendarView previously called ProjectOrganization.archivedIDs on Store.allProjects every render. Those projects already came from Store's prepared current catalog, so the watcher rebuilt the same archive graph again. Both native calendars now observe Store.archivedProjectIDs, a read-only pass-through to that catalog. There is no second cache, new persistence or cached write authority. The catalog still reads the current filtered presentation, maintains snapshot observation even on a hit and clears/revalidates all existing access/workspace/session/origin boundaries.

The current signed iPhone Simulator run passes two cases with zero failures/skips/runtime warnings. The extended production project workflow journey creates a subproject, verifies the task in Calendar, archives its parent, verifies the task hidden, restores the parent and verifies it returned. Every saved task field remains equal before/after archive, restore and cold launch. The changed Store fixture directly observes the public archived-ID reading after it is warm; both archive and restore must notify without taskRevision changing. It also checks inherited reparenting, unreadable/return, current tasks and saved snapshot preservation. No task-refresh observation can mask a missing archive notification.

The 4,000-project fixture compares twenty warm old watcher reconstructions with twenty current public reads: about231.7ms versus0.158ms total. Both expose exactly the same archived IDs. This is scoped Debug preparation in the actual Store, not a physical FPS or whole-app drop-latency result. Host/source hashes remain exact. Ten existing archive/catalog model cases also pass in each independent owner using the already-built Core products: Core/package/test inputs are unchanged, and Store.swift is explicitly excluded from that package. Those cached results are auxiliary model evidence, not current Store compilation proof; the native run provides the current iOS Store/view evidence.
