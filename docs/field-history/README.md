# Undo and Redo for independent subtask field edits

Each edit newly saved through the field editor keeps a private, encrypted record of only the fields it touched and their original values. Missing fields and explicit nulls remain distinct. Undo and Redo create fresh guarded requests; they never replay an old forward request or replace a whole historical task. Older saved requests with no original values remain retryable but do not invent an Undo.

The inverse uses the confirmed receipt revision as its field-version cutoff. A later note can survive Undo of a title/date edit. A later edit to the same field, including one changed away and back to an equal-looking value, requires review instead of being overwritten. Node incarnation, task generation, project, account and service origin remain bound. The database applies exact optional-field removals through both personal and team record authority, preserves the normal nonce/replay and terminal-closure contracts, and does not enable migration gates.

The private journal writes version 2 when original/history metadata is present; existing version-1 requests still decode. Its encrypted file path, key service and associated-data scope stay stable. An older client fails closed on the newer journal instead of silently dropping inverse metadata. Under the account/process lock, two windows recover the same saved inverse identity. Attempted inverses remain immutable and retry their original identity after lost replies. A parent receipt cannot be removed while newer Undo/Redo recovery depends on it.

Both clients add Undo/Redo to Saved subtask changes and register newly confirmed edits with their existing native history. Closing a lost request can recover its existing confirmation. Conflict review supports fields restored to an absent state. Mac window history and the iOS task menu share the same guarded operations; failed history preserves the request and points to saved recovery. The controls use existing app styles and large-text layouts.

The migration is independently owned in each repository. It has not been deployed to the hosted backend by this work. Normal migration flags remain disabled. Exact acceptance, evidence and open limits belong in verification.json; a synthetic native HTTP peer does not establish hosted SQL or genuine shared-account acceptance.

Reproduce the focused contracts with `Scripts/test_core.sh --filter 'ChildTaskFieldCommandTests|ChildTaskTransferTests|ChildTaskTransferHistoryTests|ConfirmedHistoryBridgeTests'` on Mac, or `swift test --scratch-path "$HOME/Library/Caches/TaskfoldBuild/ios-core" --filter 'ChildTaskFieldCommandTests|ChildTaskTransferTests|ChildTaskTransferHistoryTests|ConfirmedHistoryBridgeTests'` in the iOS repository. `node Scripts/Database/test-child-field-history.mjs <report.json>` uses an owned, disposable Postgres fixture, never the hosted project. The native cases are `testChildFieldsNativeSavedUndoColdRedoAndUndo` and `testChildFieldsMainListNativeUndoRedoUndo`; after exporting their reserved synthetic peer, run `python3 Scripts/verify_child_field_history_peer.py <server.json>`.

The normal full-stack `supabase db pull --local --yes` / `migration list --local` workflow could not connect to the configured local stack. The migration file was created with the CLI, then populated from directly iterated local SQL; both independently owned minimal fixtures execute that exact committed SQL and compare advisors against their fixture baseline. No hosted migration history was changed.

Acceptance on 31 October: each repo passes 133 focused client cases (six new field-history cases) and 71 tests of its own exact migration in an owned Postgres fixture, with no added advisor findings and successful container cleanup. Both full apps build and verify their signatures. Direct Mac title-edit shortcuts track the list and clean inspector through Undo/Redo/Undo and cold return. iPhone/iPad largest-text saved/cold journeys and the ordinary iPhone menu each finish with four unique requests/four writes and exact original fields. The mobile estimate journey restores an absent key, not null. Hosted deployment, genuine shared-account acceptance and wider migration work remain open.
