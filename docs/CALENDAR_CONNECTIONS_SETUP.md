# Direct calendar connection setup and acceptance

Both apps own this integration. No code, credential, provisioning input or package lockfile is loaded from the sibling repository. Existing device calendars continue to use EventKit independently.

## Provider registrations

Create a separate native app registration for each deployed bundle identifier. Public client IDs and callback schemes may be supplied as Xcode user-defined build settings; no client secret is accepted or needed. Unconfigured providers do not appear as connectable accounts. Blank client-ID defaults keep providers unavailable; the default Google callback scheme is app-specific and valid, and must be replaced by the registered reversed client ID before enabling Google.

Google: enable the Calendar API, configure the consent screen and create an **iOS-type OAuth client** for the appropriate iOS or Mac bundle identifier (Google documents this client type for both platforms). Set `TASKFOLD_GOOGLE_CALENDAR_CLIENT_ID` and `TASKFOLD_GOOGLE_CALENDAR_CALLBACK_SCHEME`. The scheme is the client ID's dot-separated components in reverse order, for example `com.googleusercontent.apps.123-synthetic` for `123-synthetic.apps.googleusercontent.com`. The full callback is that scheme followed by `:/oauthredirect`. Use the registration's actual reversed client ID. The application requests only `https://www.googleapis.com/auth/calendar.readonly`, offline access and explicit account selection/consent. No profile scope or Taskfold sign-in token is reused. Provider verification/testing-user restrictions still apply to actual consent.

Microsoft: register a public mobile/desktop client supporting the intended personal/work account audience. Set `TASKFOLD_MICROSOFT_CALENDAR_CLIENT_ID` to its application UUID. Register the exact custom callback `<actual bundle identifier>.calendar:/oauthredirect`, already declared through the app's Info.plist build expansion. The app uses the common v2 endpoint and delegated `https://graph.microsoft.com/Calendars.ReadBasic` plus `offline_access`; it does not request User.Read or write access. Tenant policies may require administrator consent. An incompatible registration must be fixed in the provider console, not bypassed in the app.

The native browser uses AppAuthCore **3.0.0**, pinned by exact version and resolved revision `a972daac82d449d58ab119e91c68153e29ddac33` separately in both Xcode projects. AppAuth generates PKCE/state and performs token exchange/refresh. The external user-agent adapter uses ASWebAuthenticationSession, not an embedded web view. Endpoints are fixed in source; remote configuration cannot change the token destination.

## Data and recovery behavior

Connect from Planner settings → Connected accounts, then select calendars explicitly. Selections and event-title preferences apply immediately; Cancel only discards the working-hours draft. Different provider-account identity requires replacement confirmation and starts with no selected calendars. Busy time includes provider-expanded recurrence instances. Free/cancelled/declined events do not count, hidden titles are omitted from read requests, and private/unknown privacy policies cannot expose event titles.

Credential records use a bundle-specific app-only Keychain service, hashed workspace/provider keys and WhenUnlockedThisDeviceOnly accessibility. They are not synchronized through iCloud Keychain, included in Taskfold exports, sent to the backend or exposed to widgets. Credential reads/writes are serialized away from the UI actor. Refresh writes require the current record identity; cancelled writes and late cleanup cannot replace/remove a newer connection. Event data is only held in memory; widgets receive derived capacity through the existing projection. Disconnect removes the saved connection on this device; it does not revoke provider consent on other devices or delete provider data. Manage global consent with Google/Microsoft.

## Verification status

Implemented: read-only API handling, staged connection state, native AppAuth/system-browser bridge, device-only secure storage, planner/capacity aggregation and account/calendar controls. Synthetic core and native-fixture checks cover only their stated cases. Provider registration/consent, physical-device/Mac credential recovery and real token-refresh/revocation/account-switch acceptance **remain required**. Synthetic OS Keychain write/update/removal now passes on phone and tablet Simulators, with all temporary records removed; that separate proof does not use real calendar credentials. No production provider consent or provider data mutation has occurred during implementation. Native visual/accessibility acceptance is recorded separately as it is completed. This work does not close remote reminders, older-client rollout or distribution gates.

The opt-in native fixture requires **both** `--uitesting` and `--calendar-links-fixture`. It restores a synthetic Google account and offers a synthetic Outlook connection. Its dedicated URLSession intercepts every request with URLProtocol and never contacts a provider; native credential installation is disabled for these launches. The additional `--calendar-native-auth-proof` flag exercises the actual AppAuth archive and native bridge with memory-only credential storage, intercepting any SDK HTTP request. The resulting `Documents/calendar-native-authorization-proof.json` contains only check names/counts, never credentials. It tests PKCE/state creation, restoration, token persistence, failure handling and a workspace switch during a held write; it does not test real consent, Keychain access or actual token refresh. Use only a separately namespaced test app, with `--planner-fixture` for the initial task workspace. It does not test OAuth consent or real Keychain behavior.
