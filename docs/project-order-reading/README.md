# Reuse project ordering during native navigation

Browse and the Mac sidebar previously read an already-cached project catalog, then rebuilt ProjectOrderRequest on every body evaluation. That repeated sorting, archive inheritance, outline construction and sibling indexing during navigation updates.

The catalog now retains its prepared active outline, and its existing source/access/workspace/session/origin cache lazily retains one immutable ordering request. Both native views use the Store accessor. Catalog misses, access changes and explicit clears retire that request. Store still reads the current readable presentation on every lookup, clears on unreadability and returns an empty request in that state. The request retains the full source; actual Move Up/Down and drag reordering still require the existing current-workspace/session/source checks. No write guard, parent, access, archive, task, manual ordering, feature gate or editor behavior is changed.

Focused tests compare source rows, outline/depth, sibling order and shifts with ordinary ordering through nested, archived, unavailable-parent, cyclic, duplicate and empty-ID graphs. They verify cache misses for every context boundary, catalog-only invalidation, stale request refusal and explicit clear. The existing ten sibling/branch ordering checks also pass. These are derived presentation values, never authorization.

In a same-host Debug diagnostic with 4,000 projects (3,600 visible), twenty previous-path requests took about 526 ms on the Mac owner and 537 ms on the iOS owner. Cached requests including a cold catalog took about 27 ms for each. Correctness comparisons run outside the timed regions. Both preserve the exact full source/outline and sibling order; there is one source read. This measures request preparation, not native rendering or physical-device FPS.
