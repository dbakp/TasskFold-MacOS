# Date phrase preferences

Taskfold now has account-owned meanings for `next week`, `this weekend` and `next weekend`. Defaults are Monday and Saturday. Choose any weekday in iOS Settings → Date phrases or macOS Settings → General → Date phrases. Changes save through the existing durable workspace queue and account-owned `view_preferences` table (`id=dates`). Local workspaces retain local choices; they do not claim cloud sync.

`next week` means the next strictly future occurrence of the chosen weekday. `this weekend` means the upcoming chosen weekend day, including today if it matches. `next weekend` skips one occurrence of that weekend day. These are civil-day calculations in the relevant calendar zone, not fixed multiples of 24 hours. The UI states these meanings; it does not reinterpret a phrase as an entire seven-day range. Combine before/after predicates for a range.

Quick entry, independent deadline braces, repeat start/end boundaries and their cursor previews use the same preference. Rescheduling menus use it too. Accepted plans, deadlines and repeat boundaries retain concrete stored dates. Changing the preference does not rewrite existing tasks, recurrence rules, notifications or undo history. Independent repeating-reminder boundaries resolve the phrase once at acceptance; weekly `every weekends` still means the existing Saturday/Sunday recurrence rule.

Saved planned/effective-due/deadline and creation-date predicates retain the phrase in their existing version-1 document. Their readers, preview counts, cache keys, capture defaults, ordered query grouping and widget projections resolve it using the current account preference. A changed preference affects relative results without changing task data. Explicit weekdays, elapsed windows, fixed instants and ordinary date predicates retain their existing meanings. A filter such as `date:next week` selects one day; it is not a next-week calendar view.

The additive deployed column is nullable and bounded, with strict version-1 numeric weekdays (Gregorian Sunday=1 through Saturday=7). Existing rows and account ownership policies remain unchanged. Known-version extra document fields survive a weekday change. Unsupported/malformed preferences disable editing and dependent filter evaluation rather than silently falling back to Monday. Missing preferences use the defaults. Settings actions carry a workspace-generation binding. Queries without these phrases retain preference-independent cache keys. Portable backups and durable queues preserve the preference and relative query; backups reject unsupported preference documents with the normal validated-restore boundary.

No preference document is added to the widget payload. Widgets receive the same bounded result IDs as ordinary saved filters (eight civil days), combined with the existing minute-expiry contract when elapsed predicates are present. Updated native clients are needed on both devices for the same interpretation. Older clients can preserve the nullable column during unrelated edits but continue their previous Monday/unsupported-filter behavior; real mixed-version/native pair acceptance remains a gate.

The current [Todoist date guide](https://www.todoist.com/help/todoist/features/schedule-a-date-and-time-for-your-todoist-tasks-q7VobO), reviewed 8 October 2026, documents configurable next-week/weekend weekdays and distinguishes this/next weekend. The [filter guide](https://www.todoist.com/help/todoist/features/introduction-to-filters-V98wIH) uses that next-week setting in relative predicates. This checkpoint implements that account-owned behavior in Taskfold's own UI. Configurable calendar week start and Todoist's broader natural-language grammar remain separate requirements.
