# Profile photo workspace ownership — 10 October 2026

Source inspection found that both native photo pickers awaited image loading/upload and then read the current profile, with no account/workspace check. A response from an old account could therefore be applied to the newly active profile. The Storage uploader also refreshed credentials before choosing its destination without retaining the initiating account. This was a source-confirmed race, not a reproduced production incident.

Both independently owned apps now capture a WorkspaceBinding when opening the picker, reject stale selections, and check that binding before upload and before saving its result. Workspace changes dismiss/reset the old picker and busy state. A per-operation token keeps an old task's completion from clearing a later operation's busy state. iOS uses the native Photos picker through explicit presentation so ownership is captured before selection rather than after return. Cancellation/account changes do not show an error on the new workspace.

Backend.uploadAvatar requires the expected account and retains the session incarnation across refresh/upload. It rejects a foreign picker before HTTP and rejects late results after sign-in or same-account reentry. The HTTP request retains the original owner's path and JWT. An already submitted upload can still finish under that original owner; the client does not apply its stale URL to a profile or attempt destructive remote cleanup.

Verification: each repository's AccountTransportTests passes 18 tests, zero failures/skips, including four new tests for stale picker ownership, held-response account switch/same-account reentry, held-refresh account switch, and successful original-owner upload. Logs: `/tmp/taskfold-avatar-scope-mac-tests-final.log` and `/tmp/taskfold-avatar-scope-ios-tests-final.log`. Both Debug native app/widget builds pass: `/tmp/taskfold-avatar-scope-mac-build.log` and `/tmp/taskfold-avatar-scope-ios-build.log`. The deterministic tests use an isolated URLProtocol at native-scope.test; no real image was uploaded at that source checkpoint. A scoped read of the disposable handoff profile confirms avatar_url remains null.

Supabase references checked before editing: [changelog](https://supabase.com/changelog.md) and [standard uploads](https://supabase.com/docs/guides/storage/uploads/standard-uploads). No relevant Storage breaking change was listed. Security review: no schema/RLS/grant/provider changes; no service key; no authorization from user metadata; original account path/JWT remain together; random paths retain existing no-upsert behavior. Existing remote-delivery gates remain in place.
