# Planner overlap layout — 5 November 2026

Both independent apps replace the repeated linear occupied-column scan with two temporary minimum heaps: ended columns become available by end time, then the lowest available column number is reused. This preserves existing visual placement, sort order, collision widths, duplicate handling, cluster boundaries and the 30-minute minimum hit target. No task/calendar mutation, persistence change or new cache is introduced. Lane assignment changes from worst-case quadratic scanning to O(n log n); input sorting is unchanged.

Each owning repository passes 32 focused Core cases. The new tests compare against the previous production algorithm over 240 deterministic mixed task/calendar inputs across ordinary, spring-forward and fall-back days. They compare identities, coordinates, column numbers/counts and original content. A separate case distinguishes lowest-column reuse from earliest-ending-column reuse, and resets after a cluster ends. Existing capacity, unknown-duration, all-day and collision tests also pass.

The diagnostic measures five runs over 4,096 synthetic simultaneously overlapping calendar items, with setup outside timing. It compares the prior algorithm with the new production function under SwiftPM Debug on this Mac. The iOS-owning module measured medians of 527.39 ms → 13.54 ms; the Mac-owning module measured 538.09 ms → 13.93 ms. No time threshold is asserted. These are calculation measurements, not physical-phone performance, rendering/FPS, native screen acceptance or a claim about typical task counts.
