# Saved completion groups and whole-group Undo

The atomic group protocol now has an encrypted, account/backend-scoped journal, a fenced sender and an observable recovery model. One entry represents the complete selection. Its attempted state must reach disk before a network call; an uncertain reply or failed confirmation save keeps that same immutable group for explicit retry. Loading never sends. Confirmations refresh authoritative tasks rather than applying historical receipt values locally. Closing a presentation or changing its account/session/workspace/access scope suppresses late confirmation and refresh.

Queued, attempted, confirmed and terminally closed groups have distinct validated states. Corrupt or duplicate-key storage is refused without overwriting it. A closed group cannot be sent again or changed to an applied outcome. A fresh reviewed replacement needs a durable terminal decision, the same targets/action and new group/member request identities. Earlier unresolved groups fence overlapping selections; checking and stopping a later group remains possible independently.

Undo requires the entire original confirmed group and fresh reads from one live scope. Every inverse member must match its own original request and confirmation. The real PostgreSQL fixture exposed reversed Undo member order; parent matching now follows request identities, while each group's wire receipt still preserves its own command order. Partial or stitched parents are refused. A second active Undo of the same original group cannot be queued. The model also checks that the read scope equals its current presentation.

History is bounded to 32 entries and 4.3 MB. Pending and stopped groups are never evicted automatically. An original and its Undo records form one retention family; settled families can be pruned together, while an unresolved Undo protects its original. A per-account process lock serializes journal read/modify/write across windows and removal tombstones block new work. Store factories use the existing encrypted backup-key mechanism, and confirmed account-removal cleanup plus synthetic-fixture reset explicitly remove the new journal.

## Acceptance limits and next work

See `verification.json` for scoped Core results, retained initial finding, exact source hashes and native build evidence. Test storage uses synthetic memory/file IO and keys. Service behavior is a typed synthetic peer using the previously verified PostgreSQL receipt fixture, not a deployed RPC round trip. The existing SQL and wire transport are unchanged; their earlier database acceptance is historical rather than a repeated run. No real task data or hosted schema changes are involved.

This verifies the recovery **core**, not the finished bulk experience. Store factories and a separate `TaskfoldChildCompletionBatchesEnabled` gate are in place, but bulk list controls, visible recovery review, fresh-read preparation and cross-operation coordination with single actions/structural work remain to connect and verify. Mixed root/child completion, full Redo/shared history, custody and broader lifecycle/workload acceptance remain open. Normal flags and server gates stay off; the broader migration checkpoint stays **To build**. Development signatures are not distribution acceptance. User deferrals remain unchanged.
