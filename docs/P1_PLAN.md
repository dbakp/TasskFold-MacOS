# P1 implementation order

User-directed scope, 20 October 2026. Ranking favors daily usefulness and preservation of existing work, then independent features, then provider/team dependencies. Both apps own their implementation and tests. Remote reminders, older-client rollout and distribution remain deferred.

| Rank | Work | Why this order | Acceptance |
| --- | --- | --- | --- |
| 1 | Nested subtask editing and organization | Existing work can contain children that the primary editors do not expose. This is a daily editing gap. | Both apps can edit/complete nested children, including notes and planning fields on both apps, add children, reorder whole branches and indent/outdent; Cancel preserves work; Save/relaunch retains metadata and stable identities; concurrent moves/edits do not duplicate children or discard their notes. |
| 2 | Saved template management | Builds directly on the newly implemented reusable workflows. | Rename/edit saved definitions, refresh from a source with review, preserve existing runs, reject unsupported versions and verify cross-device edits. Standalone interchange and a public catalog are later additions. |
| 3 | Widget manual/grouped ordering | Makes the desktop/Home Screen reflect how the user arranged the app. | My list respects supported saved ordering/grouping; additions/completions/retries retain identity and honest empty states. |
| 4 | Useful Insights and daily/weekly goals | Existing activity recording supports factual progress without invented history. | Explicit scope/time window, completion-occurrence deduplication, reopen correction, rest days and coverage-boundary messaging; matching settings/results across apps. |
| 5 | Advanced recurrence | Extends daily scheduling once organization is usable. | Multiple monthly dates with clear preview and consistent month-end/zone/count behavior; persistence, completion/Undo and cross-device fixtures. Sub-day/holiday policies require their own explicit design. |
| 6 | Direct Google/Outlook calendar connections | Useful but requires provider OAuth/reconnect and real-account acceptance. | Read-only calendars first, visible provider/account, private event handling, selected calendars and disconnect/reconnect; mirroring only after identity/deletion/loop policy and acceptance. |
| 7 | Shared activity and mentions | Depends on clear ownership, access and notification semantics. | Project-scoped activity, permission-checked mentions, departed-member safety and honest local/remote delivery state. Advanced team roles/folders/admin remain separate. |

Current status: rank 1 is delivered; ranks 2–5 are implemented with phone/tablet acceptance, while their native Mac walkthroughs await unlock. Rank 6 now includes the native sign-in/storage bridge, provider controls and planner/capacity integration; real-provider acceptance remains pending. Rank 7 has not started. The three release items remain deferred.

Already delivered: archive/restore, owner-safe subprojects, first-version private templates, reviewed multi-line capture, native assignment/member controls, guarded collection edits and the Project pulse history foundation. These are not new implementation backlog entries.

## First implementation: subtask organizer

Status: **Rank 1 is delivered for the embedded checklist model:** nested organization and child-detail editing (including notes and planning fields) are implemented in both apps. Representative native phone/tablet/Mac checks and both owned core suites pass. The organizer’s prior live transport acceptance remains recorded separately. **Rank 2 template management and rank 3 widget ordering are tracked below, with native acceptance limits stated explicitly.**

- A dedicated Organize subtasks sheet exposes the nested checklist while retaining existing inline controls.
- Each row has an editable name, completion state and actions for adding a child, sibling moves, indent/outdent and confirmed branch deletion.
- The sheet holds an isolated draft until Save; Cancel does not assign legacy identities or change saved work. A task/workspace change refuses the stale draft.
- Branches retain IDs and all existing fields, including unknown metadata. Missing legacy IDs are assigned in the explicit saved draft; malformed/duplicate identities are refused without rewriting the original.
- New nesting is bounded to ten levels, including the containing inspector depth on Mac. Existing deeper supported data stays readable.
- Current guarded transport remains in use. The collection rebase indexes identities across the tree so a moved child retains remote field changes and is not duplicated at its old location. A reviewed local layout retains remote-only children. This is not the deferred migration to independent child-task database records.
- No new task/child tables or sibling build dependency are introduced. A compatible guarded-RPC migration is included.

The list/planner progress badges count all supported checklist levels. Native iPhone/iPad checks cover Cancel, whole-branch moves, completion, composer preservation, task Save, relaunch and the 1-of-5 count. Both independently compiled cores pass real-service two-client move/order conflict/review/retry tests. ## Rank 2 — saved template management

Implemented in both repos; iPhone/iPad native acceptance and live two-client checks pass. The Mac walkthrough remains pending manual unlock, with no runtime acceptance claim. Both apps own a definition editor for template names, project/section names, task and subtask names/notes/priorities/estimates, main-task destinations, sibling order, additions, branch deletion and relative planned/deadline offsets. The editor keeps a draft until Save. Existing runs are independent records and are never updated when a definition changes. Task-level templates retain one main task.

Replace from a source captures a current project, section or task of the same kind and presents both definitions, including structure, notes, labels, repeat metadata and schedule details. Accepting that preview changes only the draft; Cancel still keeps the saved definition. A changed saved template can be compared with the draft before choosing which to keep. A removed template can be saved as a new identity. Unsupported newer definitions are preserved and cannot be overwritten by an older definition during sync review.

The shared transport contract uses the owner-only, security-invoker `taskfold_edit_template` function. Independent name and document changes merge; a definition is atomic and overlapping document edits require explicit review. Deletions guard both name and definition; retries are idempotent. Queued drafts survive remote absence and account-bound persistence, with a fresh ID on explicit recovery. This does not close the deferred older-client rollout gate.

Migrations `20261020204903_template_edit_review.sql` and `20261020205307_template_review_error_response.sql` match deployed history. Actual-role rollback tests cover independent changes, overlapping edits, review/retry, stale deletion, removal, owner isolation and anonymous denial. Live two-client tests initially exposed conflict-response timeouts with SQLSTATE 40001; the follow-up uses the existing task-edit convention (application error P0001), after which both clients pass review/retry/recovery. No assumption about the gateway’s internal retry behavior is required for that observation. Security advisors add no finding. The disposable account, sessions, refresh tokens and test records were removed.

Interchange/public catalogs remain later additions. Full native acceptance is recorded in `p1-template-management-evidence.json`; it must not be inferred from compilation or the core tests alone.

## Rank 5 — multiple monthly dates and occurrence preview

Implemented independently in both apps; representative native phone/tablet acceptance passes. Both apps independently support a monthly date set such as the 1st, 15th and 31st, with a native date selector and upcoming-occurrence preview. One current task is counted as an occurrence; completing it creates one next task. Same-month dates are visited before advancing by the chosen month interval. Late completion skips missed dates while retaining the active-month rhythm. Completion-based rules first wait the full interval, then select the next permitted date.

Short months preserve the existing last-day policy: requested dates clamp to that month's last day and collisions emit once, retaining the original date set for later months. Occurrence limits count actual emitted tasks, and inclusive end dates still apply. The preview shows the next dates if completed today, followed by completions on those displayed dates; it explains the assumption for completion-based rules and uses the task's source zone. No holiday calendar or sub-day repeat policy is added.

Quick capture accepts complete comma/and monthly date lists with existing start/end/count clauses. Invalid lists remain literal instead of silently producing a partial schedule. Single-date and ordinal-weekday rules remain supported. Rule metadata survives successor creation, queue persistence, sync and backup transfer. The local reminder engine uses the same selected dates and preserves existing reminder identities for unchanged schedules. ## Rank 6 — direct calendar connections, in progress

The independently owned read layer and workspace-bound connection state are implemented in both apps. This is a tested foundation, not a delivered sign-in feature. Native provider authorization, secure credential persistence, planner integration, calendar-selection UI and genuine provider-account acceptance remain pending. No Google/Microsoft credentials are read or stored by this phase; the shared authorizer is intentionally unavailable until the native bridge is installed. Existing device-calendar behavior is unchanged.

The read layer uses only Google Calendar GET endpoints and Microsoft Graph calendar/calendarView GET endpoints. Google requests calendar.readonly; the Microsoft contract requests Calendars.ReadBasic plus offline_access, without profile or write scopes. Recurrence instances come from the provider. All-day Google events retain their source time zone across DST. Titles are omitted from requests when hidden; private/confidential/personal events are shown as Busy, and unknown privacy policies refuse the response. Pagination stays on the original provider/resource, refuses redirects and incomplete results, and has explicit request/result bounds. Events remain in memory; this phase adds no backup, widget or server event cache.

Connections require explicit calendar selection. A different calendar account requires replacement confirmation; cancelling preserves the previous account and selection. Workspace changes, selection edits and disconnect invalidate in-flight reads, including later pagination. Expired access refreshes once; denied access, changed account identity and restoration failures stay unavailable rather than becoming free capacity. Failed credential removal hides calendars and can be retried. These behaviors use an injectable native-authorization contract; they do not demonstrate an actual OAuth consent or Keychain lifecycle yet.

Verification: 25 focused synthetic calendar cases pass independently in both repos. Full owned suites pass: iOS 807 reported / 11 environment skips / 0 failures; Mac 831 reported / 31 environment skips / 0 failures. Isolated iOS Simulator and Mac app/widget builds succeed. There is one iOS packaging warning about not stripping an already signed widget binary; no source/compiler warning. No native UI, provider consent, real credential persistence or external calendar-account acceptance is claimed by these checks. Exact evidence: `p1-direct-calendar-foundation-evidence.json`.


### Rank 6 native sign-in and planner integration

Implemented in both independently owned apps: AppAuthCore 3.0.0 with the system authentication browser, PKCE/state, a workspace-bound staged account choice, secure archive restoration and refresh persistence in a private device-only Keychain service. Public provider registrations are configured through per-app build settings; no secret is embedded, and providers remain unavailable without valid matching client/callback configuration. The package revision, privacy resource and Apache license are included in each app's own build inputs. See `CALENDAR_CONNECTIONS_SETUP.md`.

Planner settings separates device permission from direct provider accounts, shows the account identity, exposes explicit calendar choices and refresh/reconnect/disconnect, and confirms replacing a different account. Large text stacks the account actions and retains touch targets. Device and direct reads combine into the planner and derived widget capacity. Missing credentials, revoked permissions and incomplete selections remain visibly incomplete/unavailable. Local workspaces also refresh capacity when calendar choices change. Provider events are not imported into tasks or written back to calendars.

The native wrapper's offline proof uses actual AppAuth state/archive behavior with memory-only credential storage and a session that intercepts every SDK request. All 21 checks pass in the iPhone Simulator, including saved-session restoration, persistence failures, workspace isolation and conditional cleanup after switching during a held write; zero SDK HTTP requests occur. This is **not** genuine provider consent, actual Keychain acceptance or real refresh/revocation proof. The result is mirrored as iOS evidence in both repos, not claimed as Mac runtime acceptance. Native phone/tablet interaction and visual acceptance are recorded separately after verification. Real registrations/consent/Keychain and the locked Mac's walkthrough remain pending. Rank 6 is not declared delivered.


## Rank 7 readiness — shared activity and mentions

Read-only review confirms the deployed TaskFold database has RLS on tasks, project membership and the existing task-activity ledger. Dedicated comment/mention/inbox tables are not present. Current comments are embedded task JSON with client-supplied attribution, so mention delivery must not be inferred from a displayed name or an imported `@name` string. No schema or policy has been changed by this review.

Implementation order:

1. Add a project activity view using the existing permission-filtered ledger, current task/member context and explicit history coverage. Deleted/inaccessible task content must not be reconstructed from cached titles; current access determines navigation.
2. Add server-authenticated comment operations and stable IDs. Preserve legacy/imported comments as historical content without generating mentions. Bind authors and project/task identity on the server, and make retry acknowledgements idempotent.
3. Add explicit teammate selection that stores member IDs, with membership/task access rechecked atomically when a comment is sent. A stale picker or a departed member cannot create a recipient record. Cached profile names and editable JWT user metadata never grant access.
4. Add an account-owned in-app Mentions inbox with read/unread state, safe task routes and current-access checks. Keep offline/pending state distinct from an acknowledged shared comment. Push delivery remains deferred with remote reminders; no new APNs claim is introduced.
5. Verify owner/collaborator/outsider/departed-member behavior, private moves/deletions, account switches, offline retry/relaunch and import/backup preservation using disposable fixtures. Implement both native apps independently, run actual-role policy tests and advisor checks for schema changes, then commit/push each repo.

This is readiness work, not delivered rank 7 functionality. The current Supabase changelog and RLS documentation were reviewed; the upcoming CBC cipher removal is an HTTP-client compatibility item and does not authorize changing project access. Relevant sources: [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [TLS change](https://supabase.com/changelog/cbc-tls-ciphers-deprecated).
