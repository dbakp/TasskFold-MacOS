# Reuse exactly unchanged rows after refresh

Both independently owned apps now keep an immutable existing record when a refreshed row has a unique matching ID and every authored field is exactly equal. Candidate IDs use UTF-8 bytes; profiles use user_id. Missing or ambiguous IDs stay fresh, incoming order/membership are preserved, and any changed or unknown field prevents reuse. Full unchanged tables can retain their original buffer. This lets the existing bounded row encoder reuse already encoded values after sync.

Personal and team merges still apply pending work, discard unavailable history/provenance and run their existing access/privacy filtering. Team filtering occurs before reconciliation and again after queued changes; old records never supply authority. Source identity remains a nonpersistent cache proof, with domain equality and persisted formats unchanged. No external-file read, corruption, metadata-validation, staging or atomic-write safeguard was removed.

Exact string/key comparison now uses contiguous UTF-8 and a length-checked byte comparison. It does not normalize Unicode, stop at an embedded null, equate signed zeros or reinterpret opaque values. Tests cover canonical-equivalent equal-length strings, bridged/substrings, empty/null-containing text, large independent copies with a changed final byte, unknown huge values, missing/duplicate/byte-distinct IDs, profile names, order/membership, queued intent and access revocation. Each owner passes 163 selected Core cases, including twelve new functional cases and an explicit diagnostic.

The same 3,567,597-byte, 2,004-task fixture has the same hash in all five reports. Both measurements start with the existing row cache primed. The baseline encoded all 2,004 rows and took 84–87 ms. The accepted implementation encodes one changed row and reuses 2,003; the measured stage takes 50–53 ms across both independently owned Core runs, about 40% less time. The stage includes refreshed-table merge, widget metadata preparation and encoding. It excludes transport, decoding, disk write, layout, input latency and physical frame pacing. These are SwiftPM Debug measurements on this Mac, not iPhone hardware or optimized daily-build numbers.

Two intermediate versions passed their functional checks but regressed the whole measured stage: element-wise UTF-8 comparison took 204–209 ms and contiguous-buffer element iteration took 142–144 ms. Both were rejected. Their original reports remain alongside the baseline and final measurements; lower encoded-row counts alone were not acceptance. The final direct byte comparison keeps the exactness checks while improving the measured total.
