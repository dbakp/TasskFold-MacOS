# Recover the previous editable version

A saved-original review can now choose between the structure saved before the repair and the editable version held before the restoration that led to that archive. The latter is the retained newer inverse from the initial keep-older operation. It is labeled “Previous editable version” because further recoveries can retain a chronologically older version. The picker appears only when that archive has the retained source. Switching choices requests a fresh review, clears consent, shows the target structure and blocks Apply while loading. A failed choice stays visible as feedback without applying a different source.

The small saved command binds the explicit source mode, original digest, task context, fresh review digest and independent request identity. It carries no archived tree. Check, retry and Stop retain that exact identity. The new cycle retains the current editable snapshot and all current/retained file identities for Undo. Redo uses the selected target, rather than falling back to the older root. Finish and the reviewed keep-editable history workflow remain separate choices. The original archive and prior authored history stay retained; ordinary root notes and priority remain current. Recovery has no new public tables or broad grants, and current caller task/history access and archive custody remain required.

The wire mode `restore_newer` identifies the retained pre-restoration source; it is not a chronological sorting claim. Old review responses without the optional availability field remain readable by the updated clients. Older strict clients and hosted rollout still require the separately deferred upgrade verification. No normal feature flag or hosted schema is changed here.

Validation and remaining platform/lifecycle scope are recorded in verification.json. Native restore/Undo/Redo acceptance does not by itself prove every keep-editable interaction, larger-library, shared-custodian, file/audio/discussion, accessibility or cross-device case.
