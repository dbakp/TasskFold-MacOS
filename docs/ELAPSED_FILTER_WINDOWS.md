# Elapsed-time saved-filter windows

Both native repositories independently accept `date before:+4 hours`, `date after:now`, negative offsets such as `date before:-30 minutes`, and `in N minutes/hours` (including `in one minute`). Combine `date after:now & date before:+4 hours` for upcoming timed work; use the before condition alone to include older timed work. The visual Planned before/after controls accept the same references. Explicit effective-due before/after also accept them but require a timed plan: a civil-day deadline has no invented clock. Positive timed conditions exclude undated, all-day and malformed-clock tasks. NOT retains its ordinary complement when a valid reader clock is supplied.

References remain relative in the existing version-1 query document and durable queue. Canonical offsets use signed minutes or whole hours, bounded to seven elapsed days (10,080 minutes). Zero offsets use `now`; malformed/overflow/unsupported units and elapsed references in on/deadline/creation/time-only conditions are rejected. Legacy `due:`, Today, Overdue and existing civil-day/dated-clock predicates retain their meanings. No server schema, new persisted task fields or sibling build dependency is introduced.

The reader supplies an absolute instant, floored to its minute. Before excludes the boundary instant; After starts at the following minute, retaining the existing strict minute semantics. Offset hours mean elapsed seconds, including across midnight, travel and half-hour/daylight-saving changes. Fixed task plans retain their source-zone instant; floating task plans use the viewer zone. Missing/non-finite clocks fail closed through Boolean groups and negation; independent comma queries may still show their safe clock-independent results.

Active native scenes already refresh on activation, civil-day and time-zone events. Their loop now wakes at the next minute boundary. Calendar process state and affected query cache keys change without editing tasks or creating undo/sync history. Queries without elapsed windows keep clock-independent cache keys. Minute-only widget publication occurs only when a saved elapsed query exists; ordinary day/time-zone changes retain publication. This is foreground behavior, not a background execution guarantee.

Widgets receive only one day of current result IDs for an elapsed query, with `clockUpdated` and `clockValidUntil` marking a 60-second window. My list, A small window and Deadline radar add the exact expiry to their timelines. At expiry, before the projection timestamp, after a zone/day change, or for partial/non-finite/invalid windows, they request a refresh and expose no stale tasks. Ordinary saved filters keep their eight-day projections. No expression, creation metadata, assignee metadata or task notes are added to the widget payload. WidgetKit may schedule/reload later than requested; installed/provisioned host acceptance remains open.

The contract requires the app and bundled widget extension from this checkpoint. Updated native editors preserve unsupported documents and disable Save. Older clients that reject these references require a coordinated upgrade before editing them; real mixed-version/paired rollout remains unverified. Backups and offline queues retain the relative document rather than freezing the reference to a timestamp. Native acceptance and exact source inputs are recorded in `clock-window-evidence.json` and `clock-window-inputs-sha256.json`.

The [official Todoist filter guide](https://www.todoist.com/help/todoist/features/introduction-to-filters-V98wIH), checked 8 October 2026 (dated 4 September), documents hour windows and manual refresh for relative filters. This checkpoint implements bounded minute/hour windows with foreground refresh. Configurable next-week/weekend semantics, full hierarchy/collaboration grammar, full Todoist query parity, real paired account/offline/revocation/restore, Mac runtime, physical reminder delivery, installed widget hosts and release/distribution gates remain separate work.
